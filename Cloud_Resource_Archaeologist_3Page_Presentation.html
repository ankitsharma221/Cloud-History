⚠️ The Problem: Why Cloud Waste Persists

Modern cloud environments run thousands of EC2 instances, EBS volumes, and security groups. Over months and years:

1. Employee Turnover & Project Abandonment

Developers deploy infrastructure for a project, the project ends or the developer resigns, but the cloud servers stay running indefinitely.

2. The Paralysis of Fear (The Core Dilemma)

Finding idle servers is easy; having the courage to delete them is hard. SREs refuse to delete resources because nobody knows if a critical batch job or internal tool depends on them.

3. Disconnected Siloed Clues

The server ID is in AWS, the audit log is buried in CloudTrail, the code is in GitHub, and IaC state is in Terraform. No single tool stitches these facts together.

🎤 What to say in your meeting:
"Team, enterprise cloud waste isn't an inventory problem — it's an evidence problem. We waste thousands every month because engineers are terrified of breaking production if they delete unowned resources."
🎯 The Solution: The 3 Core Questions We Answer

Our Archaeologist is a deterministic system that reconstructs full provenance to answer:

Question 1: Why does it exist? (Lifecycle Timeline)

Builds a chronological story from birth to present: which Git PR, commit hash, CI/CD pipeline, and CloudTrail event launched or changed it.

Question 2: Who owns it? (Deterministic Attribution)

Applies a 5-tier fallback algorithm (Tags ➔ CODEOWNERS ➔ Account Owner ➔ Creator) with high/medium confidence ratings so you know exactly who to contact.

Question 3: Is it safe to delete? (Evidence Verdict)

Evaluates zero-traffic telemetry, unattached states, and dependencies. If audit signals are missing, the tool says "I don't know" and blocks deletion.

🎤 What to say in your meeting:
"Instead of guessing, our tool automatically answers who built it, which team currently owns it, and gives a provable risk verdict with 0 risk of breaking production."

🔐 How Approval Works

No resource is ever deleted automatically. Approval is gathered via two channels:

1. Automated Slack / Teams Alert

The bot identifies the owner and sends an interactive message with evidence and [Approve] / [Reject] buttons.

2. Role-Based UI Gating

Inside the portal, the decommissioning button is locked until an authorized engineer checks the mandatory review sign-off.

3. Full Audit Trail

Every approval, snapshot ID, and rollback reason is permanently logged in the SQLite/PostgreSQL database.

🛡️ 4-Stage Reversible Safety

Eliminates downtime fear with a staged, reversible isolation workflow:

Stage 1: Automated Snapshot

Creates an EBS/AMI backup before any configuration or network change.

Stage 2: Network Isolation & Stop

Attaches a quarantine security group (blocking ingress) and stops compute. Billing halts immediately.

Stage 3 & 4: 14-Day Canary or Rollback

Monitors for 14 days. If any service alerts, 1-click rollback restores the server in under 10 seconds.
